# Harness 设计权衡

> **不是所有任务都值得完整 Harness；应按风险动态增加约束。**

这是 Harness 设计中最重要的权衡之一。

本文讨论的是**设计方向，不是当前实现**：目前执行器固定为
Planner → Coder → Tester → Reviewer，`executionMode`、Light/Standard/Strict 分级和人工
审批节点都尚未落地。落地进度见 [里程碑路线](../milestones/milestones.md)。

## 1. 安全、规范与 Token 成本如何平衡？

建议采用**风险分级执行**：

| 任务 | 推荐流程 |
|---|---|
| 改文案、改颜色、简单样式 | 直接 Agent + 快速检查 |
| 新增普通组件 | Intake → Coder → 测试/构建 |
| 跨文件功能 | Planner → Coder → Tester → Reviewer |
| 路由、状态、依赖、权限变更 | 完整 Harness + 人工确认 |
| 高风险生产变更 | 完整 Harness + CI + 人工审批 |

不要默认所有任务都执行：

```text
Intake → Planner → Coder → Tester → Reviewer
```

可以设计成：

```text
低风险：Light Mode
中风险：Standard Mode
高风险：Strict Mode
```

### Light Mode

- 简化输入
- Coder
- type-check 或相关测试

### Standard Mode

- Intake
- Planner
- Coder
- Tester
- 必要验证命令

### Strict Mode

- 完整 Planner → Coder → Tester → Reviewer
- 文件范围检查
- 独立验证
- 人工确认
- CI 门禁

## 2. Token 应该花在哪里？

Token 不应平均分配给所有步骤，而应优先投入到高价值环节：

### 值得消耗 Token 的地方

- 复杂需求澄清
- 影响范围分析
- 复杂代码修改
- 风险审查
- 失败原因诊断

### 不值得重复消耗 Token 的地方

- 重复发送完整项目规则
- 让每个 Agent 重复阅读同一批文件
- 让 Reviewer 重复描述所有代码
- 让模型生成已经可以由脚本判断的结果
- 让 LLM 判断命令是否成功，而不是直接读取退出码

核心原则：

> **确定性问题交给脚本，语义问题交给 LLM。**

例如：

| 问题 | 应由谁处理 |
|---|---|
| JSON 是否符合 Schema | Harness |
| 命令是否返回 0 | Harness |
| 文件是否越权 | Harness |
| 组件是否满足用户意图 | LLM |
| 设计是否合理 | Reviewer |
| 是否存在业务遗漏 | LLM |

## 3. 流程太长会增加幻觉吗？

**有可能，但不是因为“步骤多”本身。**

真正增加幻觉概率的因素是：

1. **上下文过长**
   - 每个阶段都重复注入大量规则和历史；
   - 重要信息被淹没。

2. **状态漂移**
   - Planner 说一套；
   - Coder 修改后变成另一套；
   - Tester 和 Reviewer 使用过时计划。

3. **中间结果不可信**
   - Agent 自报“测试通过”；
   - 后续 Agent 直接信任自然语言，而不是实际证据。

4. **职责重叠**
   - 多个 Agent 重复分析同一问题；
   - 得出互相冲突的结论。

5. **过度追问和过度规划**
   - 简单任务被拆成很多阶段；
   - 模型开始补充不存在的需求。

所以：

> 长流程不会必然增加幻觉，但冗余上下文、重复推理和不可信中间状态会增加幻觉。

## 4. 如何降低长流程幻觉？

### 使用结构化中间产物

不要传递长篇自然语言总结，而传递：

```json
{
  "implementationPlan": [],
  "changedFiles": [],
  "verification": [],
  "issues": [],
  "approved": true
}
```

### 每个阶段只接收必要上下文

例如：

- Planner：需求、规则、相关代码摘要
- Coder：计划、目标文件、验收标准
- Tester：实际命令结果、diff 摘要
- Reviewer：diff、验收标准、验证证据

不要每次都传整个仓库。

### 让后续阶段信任机器证据

优先级应是：

```text
命令退出码 > 实际 diff > 测试报告 > Agent 自报
```

### 限制计划长度

例如 Planner 只输出：

- 3～7 个步骤；
- 受影响文件；
- 风险；
- 验收映射。

不要让 Planner 生成大段架构论文。

### 使用阶段门禁

每个阶段都应该有明确的停止条件：

```text
Planner：计划完整
Coder：代码修改完成
Tester：命令全部通过
Reviewer：显式批准
```

避免 Agent 在阶段之间无限扩展任务。

## 5. 对当前项目的具体建议（规划中）

以下内容尚未实现。当前项目可以考虑增加一个执行模式字段：

```json
{
  "executionMode": "standard"
}
```

支持：

```text
light
standard
strict
```

推荐策略：

### Light

适合：

- 单文件组件
- 文案和样式调整
- 无 API 变化的简单修改

执行：

```text
Coder → type-check/test
```

### Standard

适合：

- 新增组件
- 普通页面功能
- 多个相关文件修改

执行：

```text
Intake → Planner → Coder → Tester
```

### Strict

适合：

- 路由
- 状态管理
- 依赖升级
- 权限和配置
- 跨模块重构

执行：

```text
Intake → Planner → Coder → Tester → Reviewer → CI/人工审批
```

## 6. 一个实用判断公式

可以用简单的风险评分决定流程：

```text
风险 = 影响范围 × 修改复杂度 × 不可逆性 × 业务敏感度
```

例如：

- 修改一个局部 CSS：低风险；
- 新增 Avatar 组件：低到中风险；
- 修改 Pinia 状态：中风险；
- 修改登录流程：高风险；
- 修改 CI 权限：极高风险。

风险越高：

- 使用越完整的 Harness；
- 消耗更多 Token；
- 增加独立验证；
- 增加人工审批。

## 结论

最佳平衡不是：

```text
所有任务都强制完整 Harness
```

而是：

```text
低风险任务轻量化
中风险任务标准化
高风险任务严格化
```

并坚持三条原则：

1. **脚本验证确定性事实，LLM 处理语义判断。**
2. **中间阶段传递结构化证据，不传递冗余长文本。**
3. **安全约束应该固定存在，Agent 推理阶段可以按风险裁剪。**

这样既能控制 Token 成本，也能避免 Harness 因流程过长反而降低 LLM 的有效性。
