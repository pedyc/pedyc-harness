# 项目目标

> **Run AI agents under explicit contracts, policies, and verification gates.**
>
> 让 Agent 在契约、策略和独立验证的约束下可靠执行任务。

本文是 `docs/` 的基准文档，回答四个问题：**定位是什么、按什么原则做、先做什么、明确不做什么**。
已经做到哪一步见 [里程碑路线](./milestones.md)。实现细节分散在其余文档：
[项目架构](./architecture.md)、[Preset 设计](./preset-design.md)、
[Provider 设计](./provider-design.md)、[CLI 使用与生成规则](./cli.md)、
[发布与版本规则](./release.md)、[Harness 设计权衡](./Harness设计权衡.md)。

## 一、定位：Agent 的控制平面

Claude Code、Codex 这类 Coding Agent 已经把
「理解代码库 → 规划 → 改文件 → 跑命令 → 观察结果 → 修复」这条链做得很成熟，而且仍在快速
进化。再做一个同一层的东西没有优势，也没有必要。

Harness 回答的是另一组问题：

| | Coding Agent | pedyc-harness |
| --- | --- | --- |
| 回答的问题 | 这个活怎么干完 | 这次任务**允许**干什么，干完**凭什么**算数 |
| 核心资产 | 模型、上下文、工具调用 | 契约、策略、独立验证、证据、审计 |
| 边界所在 | Agent 自身的能力上限 | Agent 之外的约束与判定 |
| 失败模式 | 干得不够好 | 约束不住、验不出来、查不清楚 |
| 与 Agent 的关系 | — | 是 Agent 的宿主，不是它的竞品 |

关键推论：

> **Agent 越强，Harness 越重要。** Agent 是执行者，Harness 是控制平面。

在需要治理的场景里，任务不会交给「随便改代码 → 跑几个测试 → 说完成了」的流程，而是：

```text
Task
 ↓
Contract        这次要做什么，验收标准是什么
 ↓
Policy          这次允许碰哪些文件、跑哪些命令、花多少时间
 ↓
Agent Runtime   Claude Code / Codex / 其他，作为可替换的执行组件
 ↓
Changes         Agent 产出的实际文件改动
 ↓
Validation      Harness 自己执行门禁，不采信 Agent 的自述
 ↓
Gate            Policy 复核 + Reviewer 判定 + 可选人工审批
 ↓
Result / Audit  PASS / FAIL，附可复核的证据链与执行轨迹
```

Harness 的价值随接入的 Agent 增多而上升：接入的 Agent 越多、越强，统一约束、统一验证、
统一审计的需求越强。这也是 Provider 抽象值得做、但不值得当作核心的原因。

## 二、设计原则

1. **Agent 是执行者，不是主体。** Harness 的设计对象是「Agent 之外的约束」，不是 Agent
   自身的能力。任何让 Harness 变得更像 Agent 的改动，都需要重新论证。
2. **不信任 Agent 的自我描述。** Agent 返回 `"tests": "all passed"` 不构成证据。Harness 必须
   自己执行门禁，并记录命令、退出码和输出。这是本项目最重要的一条原则。
3. **策略回答的是「这次允许干什么」，而不是「Agent 能干什么」。** 权限是任务级的，
   不是工具级的。
4. **任何写入都必须可判定范围。** 文件改动要么落在 `allowedProductPaths` 内，要么失败；
   `protectedPaths` 命中即拒绝，而不是只做记录。
5. **过程必须可审计。** 一次运行结束后应当能回答：跑了哪些阶段、各花多久、执行了哪些命令、
   退出码是多少、谁批准、依据是什么。
6. **流程与技术栈解耦。** 编排逻辑属于 Runtime；技术栈规则通过 Preset 注入；两者都不得
   复制对方的逻辑。
7. **项目规则保存在项目自身。** 契约、策略和 Prompt 生成到目标项目并纳入版本控制，
   而不是隐藏在 npm 包里。
8. **Provider 可插拔，但 Provider 不是核心。** Adapter 的成功标准是「换成别的 Agent 也不用
   改 Harness」，而不是「支持尽可能多的 Agent」。
9. **初始化可重复执行，且不覆盖用户修改。** `init` 幂等，只有 `--force` 才覆盖模板文件。
10. **默认拒绝扩张。** 面对 Memory、RAG、MCP、Multi-Agent、模型路由这类能力，默认结论是
    「不做」，除非能证明它直接服务于约束、验证或审计。

原则的落地状态逐条对应到 [里程碑路线](./milestones.md) 中的验收标准。

## 三、能力优先级与现状

优先级来自定位，现状来自代码核查——两者经常不一致，因此分开列出。

| 方向 | 优先级 | 现状 |
| --- | --- | --- |
| Policy Engine | ⭐⭐⭐⭐⭐ | **部分**：`allowedProductPaths` 会拦截文件改动；`forbiddenCommands` 无任何代码读取，`protectedPaths` 只被校验为数组、从不用于拦截 |
| Independent Verification | ⭐⭐⭐⭐⭐ | **部分**：Tester 独立执行门禁、不采信 Coder 自述；但缺证据结构与命令输出留存 |
| Diff / Scope Enforcement | ⭐⭐⭐⭐⭐ | **部分**：只有基于文件路径的检查，不覆盖命令层 |
| Approval Gate | ⭐⭐⭐⭐⭐ | **未实现**：无人工审批节点 |
| Execution Trace / Audit | ⭐⭐⭐⭐⭐ | **部分**：落盘 `input/policy/iteration-*/output`；无事件流、无耗时、无 `runs` 管理 |
| Task Contract | ⭐⭐⭐⭐⭐ | **已实现**：`.harness/*.schema.json` + Ajv 校验 |
| Agent Adapter | ⭐⭐⭐ | **部分**：协议已定；仓库内 Adapter 仍硬编码本仓库路径与门禁名 |
| Web Dashboard / 执行可视化 | ⭐⭐ | **未实现**：先让 Trace 数据落地，再谈展示 |
| 非 CLI Provider（HTTP API） | ⭐ | **不排期** |
| Multi-Agent / MCP / RAG / Memory | 不做 | 见第四节 |

当前最刺眼的落差是：五个 ⭐⭐⭐⭐⭐ 方向里有三个是「部分」、一个是「未实现」，而 ⭐⭐⭐ 的
Adapter 反而是文档里规划得最细的。第二阶段的里程碑因此改为以治理能力为主线。

## 四、非目标

以下方向明确不做。它们会把项目拖回「再做一个 Agent 平台」，与第一节的定位直接冲突：

- **不做自己的 Coding Agent。** 不训练、不微调、不自建 Planner/Coder 模型体系。
- **不做 Claude Code / Codex 的替代品。** 不追求「比它们更会干活」。
- **不做 Multi-Agent Framework。** 不做子 Agent 分工、结果合并、Agent 间通信。
- **不做 Memory / RAG / 向量检索。** 上下文管理交给 Agent 自身。
- **不做 MCP / 工具生态。** 工具边界由 Provider 和被接入的 Agent 决定。
- **不做模型路由与 Prompt 自动优化。** 不按任务挑选模型。
- **不把 Provider 数量当作指标。** Provider 抽象的目的是可替换，不是覆盖面。
- **不做会话式交互。** 输入是一次任务契约，不是一段对话。

这些不是「暂时不做」，而是「按当前定位不应该做」。将来若确实要做，应当先修改第一节的
定位，再写代码，而不是反过来。

## 五、实现设计：分层

```text
CLI
└── Runtime
    ├── Intake and JSON Schema validation
    ├── Policy and scope enforcement
    ├── Agent orchestration
    ├── Independent verification
    ├── Diff inspection
    └── Run records and structured output

Project configuration
├── .harness/*.json
├── AGENTS.md
└── package.json verification scripts

Preset
└── generic, vue, or a project-owned preset
```

分层的详细职责边界见 [项目架构](./architecture.md)。

Harness 与技术栈解耦这件事已经落地：Runtime 不引用 Vue，Vue 约束全部下沉到
`@pedyc/harness-preset-vue`，`examples/` 下的 non-Vue 样例可以证明这一点。后续新增技术栈
应当只增加 Preset，不修改 Core。

## 六、实现设计：包拆分与 Preset

四个包同步发布，共享版本号：

| 包 | 目录 | 职责 |
| --- | --- | --- |
| `@pedyc/harness-core` | `packages/core` | Runtime 原语，不依赖 Vue |
| `pedyc-harness` | `packages/cli` | 自包含 CLI 与 Preset Registry |
| `@pedyc/harness-preset-generic` | `packages/preset-generic` | 通用契约与安全策略 |
| `@pedyc/harness-preset-vue` | `packages/preset-vue` | Vue 3 + TypeScript + Vite 约定 |

Preset 只包含项目差异，不包含流程实现：

```ts
type HarnessPreset = {
  name: string
  allowedProductPaths: string[]
  protectedPaths: string[]
  requiredChecks: CheckDefinition[]
  instructionTemplates: string[]
  agentTemplates: string[]
  skillTemplates: string[]
}
```

Vue Preset 与 Node 风格 Preset 的差别应当只体现在这几项上。新增 Preset 不得修改 Core。
接口细节见 [Preset 设计](./preset-design.md)；版本与发布规则见
[发布与版本规则](./release.md)。

## 七、实现设计：CLI 与项目生成文件

```text
pedyc-harness
├── init       初始化 Harness，生成契约、策略与模板
├── verify     检查配置和项目环境
├── run        执行四阶段闭环
├── doctor     检查 Provider 和项目环境
├── update     更新生成的模板
└── diff       查看模板与项目文件的差异
```

npm 包提供稳定的运行时和模板；CLI 把适配当前项目的配置、脚本和原理解释生成到项目中：

```text
npm 包
├── CLI 与 Harness runtime
├── JSON Schema
└── Preset templates

目标项目（纳入版本控制）
├── .harness/     契约、策略、运行记录
├── .agents/      Skills
├── .github/      Agents、Instructions、CI
├── AGENTS.md
└── package.json  scripts
```

生成到项目而不是每次从 `node_modules` 读取，是为了让规则可被审查、可随项目演进、
CI 不依赖隐式的包内容。

初始化必须可以安全地重复执行：默认只创建不存在的文件，已有文件保留；`update` 升级模板但
默认跳过被修改过的文件；只有 `--force` 才显式覆盖。命令细节见
[CLI 使用与生成规则](./cli.md)。

## 八、实现设计：Provider

Agent 角色通过 `provider` 名称路由到 Adapter，而不是直接绑定命令：

```json
{
  "providers": {
    "claude": { "command": "node", "args": ["scripts/harness/claude-adapter.mjs"] }
  },
  "coder": { "mode": "external", "provider": "claude" }
}
```

Adapter 协议固定为：从 stdin 读取一个 Harness JSON 请求，向 stdout 写出一个 Agent JSON
响应，stderr 记录诊断，用退出码报告失败。

`doctor` 负责检查 Provider 命令是否存在、当前项目是否满足配置、必需的 npm scripts 是否
存在、目标目录是否可写。

按第八条设计原则：Provider 只解决「换一个 Agent 要不要改 Harness」，不解决「支持多少种
Agent」。协议细节见 [Provider 设计](./provider-design.md)。

## 九、提示词分层（设想，尚未实现）

规则不应整体硬编码在 npm 包里。目标是运行时把四部分组合后交给 Provider：

```text
core instructions      # 契约、阶段流程、安全策略，所有项目通用
+ preset instructions  # 技术栈约定，例如 Vue 3 <script setup lang="ts">
+ project instructions # 项目自身规则，来自项目中的 AGENTS.md
+ task payload         # 本次任务输入
```

**当前状态**：这一段拼接在代码中并不存在。`init` 会生成 `AGENTS.md`，但请求里不包含它，
实际依赖被接入的 Agent CLI 自行按工作目录读取。因此本节的四段式应视为设计意图，
而不是已实现行为。[项目架构](./architecture.md) 中对同一处的描述同样属于设想。

## 十、配置形态

目标形态是稳定的项目配置：

```json
{
  "$schema": "https://pedyc.dev/harness/config.schema.json",
  "preset": "vue",
  "productPaths": ["src/"],
  "protectedPaths": [".github/", ".claude/", ".agents/", ".harness/", "scripts/"],
  "checks": [{ "name": "type-check", "command": "npm run type-check" }],
  "agents": { "coder": "claude" },
  "maxIterations": 3
}
```

当前实现仍使用按职责拆分的多个 JSON 文件（schema、policy、agents、evaluation 各自独立），
便于版本管理和安全审查。是否合并为单一 `config.json` 尚未决定；即便合并，Policy 仍应保持
可单独审查。

## 十一、演进顺序

第一阶段（M0–M6）已完成：从 Vue 示例抽离出通用 Core、Preset 和可发布 CLI，并具备打包与
安装验证。**第二阶段改为以治理能力为主线**，因为上面第三节的核查显示，五个核心方向里三个
只是部分实现、一个完全未实现。

演进原则：

1. 治理能力优先于 Agent 能力。
2. 先让约束可执行，再让过程可观察，最后才是可移植。
3. 每个里程碑都要能回答「它增强了哪一条设计原则」。

具体里程碑、工作项和验收标准见 [里程碑路线](./milestones.md)。
