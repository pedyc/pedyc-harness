# 项目目标

> **Run AI agents under explicit contracts, policies, and verification gates.**
>
> 让 Agent 在契约、策略和独立验证的约束下可靠执行任务。

本文是 `pedyc-harness` 的项目基准文档。

它只回答：

1. 为什么需要 Harness
2. pedyc-harness 是什么
3. 核心运行模型是什么
4. 遵循哪些设计原则
5. 明确不做什么
6. 当前阶段重点是什么

具体实现见其他设计文档。

---

## 一、项目定位

Claude Code、Codex 等 Coding Agent 已经能够完成：

```text
理解代码库
→ 规划
→ 修改文件
→ 执行命令
→ 观察结果
→ 修复
```

pedyc-harness 不再重复构建这一层能力。

它解决的是另一类问题：

> **这次任务允许 Agent 做什么，以及完成之后凭什么认为任务真的完成了。**

因此：

|          | Coding Agent           | pedyc-harness                                   |
| -------- | ---------------------- | ----------------------------------------------- |
| 核心问题 | 怎么把任务完成         | 什么可以做、什么算完成                          |
| 核心资产 | 模型、上下文、工具调用 | Contract、Policy、Verification、Evidence、Audit |
| 角色     | 执行者                 | 控制平面 / 宿主                                 |
| 关注点   | Agent 能力             | Agent 之外的约束与判定                          |

核心关系：

> **Agent 是执行者，Harness 是控制平面。**

因此：

> **Agent 越强，Harness 越重要。**

在此基础上，项目的目标定位可以进一步收敛为：

> **Declarative Governance Runtime for AI Agents**（面向 AI Agent 的声明式治理运行时）

Agent 只负责执行，治理策略由项目声明；声明可以继承、复用、分层共享，最终被编译成可执行的
约束。这要求 Harness 先具备配置层：能力由 npm 安装，治理模型由 `.harness/` 声明，Preset 提供
可复用的默认能力。见 [核心架构](./核心架构.md) 与 [Preset 设计](./Preset设计.md)。

## 二、核心运行模型

一次任务遵循：

```text
Task
 ↓
Contract
 ↓
Policy
 ↓
Agent Runtime
 ↓
Actual Changes
 ↓
Independent Verification
 ↓
Gate
 ↓
Result / Audit
```

各阶段职责：

* **Contract**：定义任务目标与验收标准
* **Policy**：定义本次任务允许修改什么、执行什么
* **Agent Runtime**：调用 Claude Code、Codex 或其他 Agent
* **Actual Changes**：检查实际产生的文件改动
* **Independent Verification**：Harness 自己执行验证
* **Gate**：进行策略复核、验收判定、必要时人工审批
* **Result / Audit**：输出最终结果与可复核证据

关键原则：

> Agent 的自我描述不是独立验证证据。

例如 Agent 返回：

```json
{
  "tests": "all passed"
}
```

不能直接作为任务通过的依据。

Harness 必须自行执行验证，并记录：

* command
* exit code
* stdout
* stderr
* duration
* timestamps

## 三、设计原则

### 1. Agent 是执行者，不是主体

Harness 关注的是：

> Agent 之外的约束、验证与审计。

不以增强 Agent 自身能力为核心目标。

### 2. 不信任 Agent 的自我描述

Agent 报告成功不等于任务成功。

验证必须由 Harness 独立执行。

### 3. Policy 是任务级约束

Policy 回答：

> **这一次允许 Agent 做什么？**

而不是：

> Agent 理论上能做什么？

### 4. 所有写入都必须可判定范围

文件修改必须能够判断是否位于允许范围内。

原则上：

```text
allowedProductPaths
        ↓
允许修改

protectedPaths
        ↓
禁止修改
```

### 5. 过程必须可审计

一次运行结束后，应能够回答：

* 执行了哪些阶段
* 执行了哪些命令
* 每个阶段耗时多久
* 验证是否通过
* 修改了哪些文件
* 最终为什么通过或失败
* 是否经过人工批准

### 6. Runtime 与技术栈解耦

Runtime 不应该知道 Vue、React 等具体技术栈规则。

技术栈差异通过 Preset 提供。

```text
Runtime
   ↑
Preset
   ↑
Project
```

### 7. 项目规则属于项目本身

契约、Policy、AGENTS.md 等项目规则应生成到目标项目，并纳入版本控制。

不要把关键规则隐藏在 npm 包内部。

### 8. Provider 可插拔，但不是核心

Provider 的目标是：

> 换一个 Agent，不需要修改 Harness。

而不是：

> 尽可能支持更多 Agent。

### 9. 初始化必须幂等

`init` 默认：

* 不覆盖已有文件
* 只创建不存在的文件

只有显式使用 `--force` 才允许覆盖。

### 10. 默认拒绝扩张

以下能力默认不属于项目目标：

* Multi-Agent
* MCP
* RAG
* Memory
* 模型路由
* Prompt 自动优化

如果未来需要这些能力，应首先重新论证项目定位。

### 11. 配置是治理声明，不是包元数据

目标形态下，Harness 配置属于 `.harness/harness.json`，不塞进 `package.json`。

```text
package.json     依赖、脚本、包元数据
.harness/        治理模型：Policy / Verification / Agent / Rules
```

两者语义不同、生命周期不同。混在一起会让 Harness 的 schema 演进被 npm 项目的 schema 演进绑架。

原则：

> 简单项目只维护一个 Manifest，复杂项目才拆分文件。

不要要求用户一开始就手工维护一整套配置文件。

### 12. 治理定义进入版本库，运行时状态不进入

```text
.harness/harness.json
.harness/policy.json
.harness/rules/
.harness/tasks/
        ↓
Governance Definition，应该提交

.harness/runs/
        ↓
Runtime State / Audit Data，应该 gitignore
```

### 13. 安全约束只能收紧，不能放宽

默认值类配置可以被更高层级覆盖；安全类约束不能被任何层级移除。

```text
个人 Preset：允许 git push
公司 Preset：禁止 git push
        ↓
      DENY
```

因此配置优先级不是简单的「高层级覆盖低层级」，而是默认值与安全约束两条不同的合并规则，
见 [Policy 设计](./Policy设计.md)。

### 14. 复用通过 npm 分发，不自建 Registry

Preset 是普通 npm package。团队共享治理配置的方式是发布包，而不是复制文件。

Harness 只负责解析、合并和校验，不承担分发、托管和版本管理。

## 四、明确不做

### 不做自己的 Coding Agent

不训练、不微调、不构建自己的 Planner / Coder 模型体系。

### 不做 Claude Code / Codex 替代品

不追求：

> “比 Coding Agent 更会写代码。”

### 不做 Multi-Agent Framework

不负责：

* 子 Agent 分工
* Agent 间通信
* Agent 结果合并

### 不做 Memory / RAG

上下文管理交给 Agent。

### 不做 MCP / Tool Ecosystem

工具能力由 Provider 与 Agent 决定。

### 不做模型路由

不根据任务自动选择模型。

### 不以 Provider 数量作为指标

Provider 抽象的价值是：

> **可替换性，而不是覆盖数量。**

### 不做会话式 Agent

Harness 的基本输入是：

> 一次明确的 Task Contract

而不是长期聊天会话。

### 不做自建 Preset Registry

Preset 复用 npm registry：

```text
public package
private package
GitHub Package Registry
企业自建 npm registry
```

Harness 不承担 Preset 商店、上传平台或版本管理器的职责。需要搜索、安装、发布 Preset 时，
优先复用 npm 生态已有的能力，而不是先建一个自有 Registry。

## 五、当前阶段

第一阶段 M0–M6 已完成：

```text
Vue 示例
    ↓
通用 Core
    ↓
Preset
    ↓
可发布 CLI
    ↓
安装 / 打包验证
```

当前阶段分两步推进，顺序有先后：

```text
第一步  Config Manifest（harness.json）      M15
        ↓
        Preset Resolution（npm 分发 + 继承）  M16
        ↓
第二步  Policy Enforcement                    M7
        ↓
        Independent Verification              M8
        ↓
        EffectiveHarnessConfig（合成生效配置） M17
        ↓
        Trace / Audit · Approval Gate         M9 · M10
```

第一步先做的原因是依赖顺序，不是偏好：配置层决定 Policy、Verification 与 Run Record 从哪里
读配置。先实现强制执行，再引入 Manifest 与 Preset 解析，会让加载层和记录格式各返工一次。

第二步按优先级完善治理能力：

1. Policy Enforcement
2. Independent Verification
3. Diff / Scope Enforcement
4. Approval Gate
5. Execution Trace / Audit

配置层的价值不在「约束是否可执行」，而在「约束能否被声明、复用和共享」。没有它，团队治理只能
靠复制文件传播。阶段划分、依赖关系与验收标准见 [里程碑路线](./milestones.md)。

当前能力状态以代码核查和 `milestones.md` 为准，不在本文维护详细实现状态。

## 七、项目核心公式

pedyc-harness 不负责证明：

> Agent 很聪明。

它负责证明：

> **任务是否符合 Policy、实际修改是否符合 Scope、验收是否拥有独立 Evidence。**

因此核心结果可以抽象为：

```text
Result
=
Policy Evaluation
+
Independent Evidence
+
Change Inspection
```
