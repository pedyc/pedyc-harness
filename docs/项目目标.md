# 项目目标

> **通用核心 CLI + 技术栈 Preset + 项目级配置 + 可插拔 Agent Provider**

本文是 Harness 的产品目标基准：`docs/` 下其他文档描述的分层、配置和扩展方式都应与本文对齐。
本文回答「要做什么、为什么这样拆分」；已经实现到哪一步、每个阶段的验收标准，见
[里程碑路线](./milestones.md)。文中标注为设想或建议的部分，不代表当前已经实现。

## 一、当前实现中需要抽离的部分

目前仓库已经具备比较好的 Harness 基础，但仍有明显的 Vue 项目耦合：

- `scripts/harness/run.mjs` 将 Harness 根目录固定为当前仓库根目录，并直接读取 `.harness/`
- `verify-config.mjs`（现已迁移为项目级 `.harness/verify.mjs` 钩子）固定检查 Vue 项目相关文件
- `policy.json` 默认只允许修改 `src/`
- `input.schema.json` 目前虽然比较通用，但 `$id` 仍带有 Vue Harness 命名
- `AGENTS.md` 明确规定了 Vue 3、`src/`、`vue-tsc` 等约束
- 当前默认检查项包含 `type-check`、`test:unit`、`build`，这些并不是所有项目都具备

因此，应该把当前项目拆分为两层：

```text
通用 Harness Core
├── 任务输入输出契约
├── Planner → Coder → Tester → Reviewer 流程
├── Agent Provider 路由
├── 文件变更检测
├── 路径权限控制
├── 命令执行与验证
├── 运行记录与 JSON 输出
└── CLI

项目 Preset
├── Vue
├── React
├── Node.js
├── Python
├── Go
└── custom
```

## 二、推荐的用户体验

理想情况下，其他项目只需要执行：

```bash
npm install --save-dev pedyc-harness
npx pedyc-harness init
```

CLI 自动询问或检测：

```text
Detected project: React + TypeScript + Vite

Choose a harness preset:
❯ react
  generic
  custom

Select agent provider:
❯ claude
  copilot
  custom
```

然后生成：

```text
.harness/
├── input.schema.json
├── output.schema.json
├── task.schema.json
├── agent-response.schema.json
├── policy.json
├── evaluation.json
├── agents.json
└── task.example.json

.harness/runs/
.agents/
├── skills/
└── ...

.github/
├── agents/
├── instructions/
└── workflows/harness-verify.yml

AGENTS.md
```

并在目标项目的 `package.json` 中添加：

```json
{
  "scripts": {
    "harness:verify": "pedyc-harness verify",
    "harness:run": "pedyc-harness run",
    "harness:dry-run": "pedyc-harness run --dry-run --json"
  }
}
```

之后用户可以直接运行：

```bash
npm run harness:verify

npm run harness:run -- \
  --input .harness/task.json \
  --dry-run \
  --json
```

## 三、npm 包应该如何拆分

我建议不要只发布一个“大包”，而是内部按职责拆分。

### 1. 核心包

例如：

```text
@pedyc/harness-core
```

负责：

- 输入任务解析
- JSON Schema 校验
- Agent 阶段编排
- Provider 调度
- 文件快照和变更检测
- 受保护目录校验
- 命令执行
- 运行记录
- 结构化输出

### 2. CLI 包

例如：

```text
pedyc-harness
```

负责：

```bash
pedyc-harness init
pedyc-harness verify
pedyc-harness run
pedyc-harness doctor
pedyc-harness list-presets
pedyc-harness update
```

如果希望使用体验简单，也可以先将 CLI 和 Core 放在同一个 npm 包里。

### 3. Preset 包

例如：

```text
@pedyc/harness-preset-vue
@pedyc/harness-preset-react
@pedyc/harness-preset-node
@pedyc/harness-preset-python
```

Preset 不应该包含流程实现，而应包含项目差异：

```ts
type HarnessPreset = {
  name: string
  detect(root: string): Promise<boolean>
  allowedProductPaths: string[]
  protectedPaths: string[]
  requiredChecks: CheckDefinition[]
  instructionTemplates: string[]
  agentTemplates: string[]
  skillTemplates: string[]
}
```

例如 Vue Preset 可以定义：

```json
{
  "name": "vue",
  "allowedProductPaths": ["src/"],
  "requiredChecks": [
    "npm run harness:verify",
    "npm run type-check",
    "npm run build"
  ],
  "conventions": [
    "Use Vue 3 script setup with TypeScript",
    "Use PascalCase for components"
  ]
}
```

而 Node.js Preset 可以定义：

```json
{
  "name": "node",
  "allowedProductPaths": ["src/", "test/"],
  "requiredChecks": [
    "npm test",
    "npm run build"
  ]
}
```

## 四、不要把提示词完全硬编码在 npm 包中

你的设想中“通过 CLI 构建通用脚本和提示词文件”是可行的，但提示词最好分成三层：

### 1. Core Prompt

所有项目通用：

```text
你需要按照输入契约、执行策略和质量门禁完成任务。
流程为 Planner → Coder → Tester → Reviewer。
不得修改受保护目录。
必须返回结构化 JSON。
```

### 2. Preset Prompt

技术栈相关：

```text
使用 Vue 3 <script setup lang="ts">。
组件 Props 必须显式声明类型。
```

### 3. Project Prompt

项目自身规则：

```text
本项目使用 pnpm。
业务代码位于 packages/web。
不得修改 generated/。
```

最终执行时组合为：

```text
core instructions
+ preset instructions
+ project instructions
+ task payload
```

这样可以避免为了支持一个新项目而复制整套 Harness 逻辑。

## 五、建议的配置文件

可以设计一个稳定的项目配置，例如：

```json
{
  "$schema": "https://pedyc.dev/harness/config.schema.json",
  "preset": "vue",
  "productPaths": ["src/"],
  "protectedPaths": [
    ".github/",
    ".claude/",
    ".agents/",
    ".harness/",
    "scripts/"
  ],
  "checks": [
    {
      "name": "type-check",
      "command": "npm run type-check"
    },
    {
      "name": "unit-test",
      "command": "npm run test:unit"
    },
    {
      "name": "build",
      "command": "npm run build"
    }
  ],
  "agents": {
    "planner": "claude",
    "coder": "claude",
    "tester": "claude",
    "reviewer": "claude"
  },
  "maxIterations": 3
}
```

可以考虑使用：

```text
.harness/config.json
```

替代当前多个配置文件中的一部分，但 Schema、Policy、Agent 配置仍可以保持独立，便于版本管理和安全审查。

## 六、Provider 设计应当保持可插拔

当前 `agents.json` 已经有 Provider 抽象，这是很好的方向。

建议统一为 Adapter 接口：

```ts
export interface AgentProvider {
  run(input: AgentRequest): Promise<AgentResponse>
}
```

内置 Provider 可以包括：

```text
claude-cli
copilot-cli
openai-api
anthropic-api
custom-command
```

配置示例：

```json
{
  "providers": {
    "claude": {
      "type": "command",
      "command": "claude",
      "args": []
    },
    "custom": {
      "type": "command",
      "command": "my-agent",
      "args": []
    }
  }
}
```

需要注意的是，npm 包本身不应默认假设用户已经安装或登录了某个 Agent CLI。可以通过：

```bash
pedyc-harness doctor
```

检查：

- Provider 命令是否存在
- CLI 是否可执行
- 当前项目是否满足配置
- 必须的 npm scripts 是否存在
- 目标目录是否可写
- Git 工作区是否干净或存在未提交改动

## 七、CLI 初始化时不要无条件覆盖文件

这是 npm 初始化工具最容易出问题的地方。

建议默认行为：

```bash
pedyc-harness init
```

只创建不存在的文件；如果文件已经存在：

```text
.harness/policy.json already exists.
❯ Keep existing file
  Merge generated defaults
  Replace file
```

同时提供：

```bash
pedyc-harness init --preset vue
pedyc-harness init --force
pedyc-harness update
pedyc-harness diff
```

其中：

- `init`：首次安装
- `update`：升级 Harness 模板
- `diff`：查看模板与项目文件的差异
- `--force`：明确允许覆盖，不应作为默认行为

## 八、最值得优先抽象的部分

我建议按以下顺序演进。

### Phase 1：先让当前仓库具备“项目根目录无关性”

把 `run.mjs` 改为接受：

```bash
pedyc-harness run --root <project-root>
```

或者运行时使用：

```ts
process.cwd()
```

不再依赖 npm 包自身的目录结构。

同时将以下内容从代码中抽出：

- `.harness` 的位置
- 必须检查的文件
- 允许修改的目录
- 必须执行的命令
- Agent 配置路径
- 运行记录路径

### Phase 2：抽出 Generic Preset

先实现：

```text
generic
```

它只提供：

- 通用契约
- 通用流程
- 通用安全策略
- 用户自行配置的验证命令

然后再将现有 Vue 规则迁移成：

```text
vue
```

这一步可以验证当前代码确实不再依赖 Vue。

### Phase 3：实现 `init` CLI

例如：

```bash
npx pedyc-harness init --preset generic
npx pedyc-harness init --preset vue
```

生成模板、配置、Instructions、Agent 文件和 npm scripts。

### Phase 4：拆出独立 Preset 包

当 React、Node、Python 等 Preset 真正出现时，再拆成独立包。不要一开始就为了未来场景建立过度复杂的插件系统。

## 九、关于“生成脚本和提示词文件”的结论

这个方向是正确的，但建议定义为：

> npm 包提供稳定的运行时和模板；CLI 将适配当前项目的配置、脚本和提示词生成到项目中。

也就是说：

```text
npm 包
├── CLI
├── Harness runtime
├── JSON Schema
├── Core prompt
├── Preset templates
└── Provider adapters

目标项目
├── .harness/
├── .agents/
├── .github/
├── AGENTS.md
└── package.json scripts
```

而不是每次执行时直接依赖 `node_modules/pedyc-harness` 内部的模板文件。生成到目标项目的好处是：

- 规则可以随项目版本控制
- CI 不依赖隐式的 node_modules 内容
- 团队成员可以审查提示词和策略
- 可以对不同项目进行定制
- Harness 升级时可以通过 diff 观察变化

## 十、我的总体建议

可以采用如下产品形态：

```text
pedyc-harness
├── init       初始化 Harness
├── verify     检查配置和项目环境
├── run        执行 Planner/Coder/Tester/Reviewer
├── doctor     检查 Provider 和项目环境
├── update     更新生成的模板
├── diff       查看模板差异
└── presets    generic/vue/react/node/python
```

推荐的第一版安装方式：

```bash
npm install --save-dev pedyc-harness
npx pedyc-harness init --preset vue
npm run harness:verify
```

最重要的架构原则是：

1. **Harness 流程与技术栈解耦**
2. **技术栈规则通过 Preset 注入**
3. **项目规则保存在项目自身，而不是隐藏在 npm 包里**
4. **Agent Provider 可插拔**
5. **CLI 初始化必须可重复执行且不覆盖用户修改**
6. **安全策略、路径白名单和验证命令必须是显式配置**
7. **先抽象 Generic + Vue，再扩展其他生态**

所以，答案是：**通过 npm 包和 CLI 分发完全可行，而且很适合这个项目；但应把它设计成“可生成项目级 Harness 的工具链”，而不是单纯把当前 Vue 仓库打包发布。**
