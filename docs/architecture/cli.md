# CLI 架构

> CLI 是用户入口,也是唯一会**改动目标项目文件**的组件。
>
> 参数、写入产物与退出码见 [CLI 契约](../interfaces/cli.md)。本目录只回答:是什么、什么时候执行、
> 如何参与决策。

## 1. 是什么

CLI 有两个身份:

1. **项目初始化器** —— `init` / `update` 把 Preset 展开成目标项目里的治理文件。这是唯一会写目标
   项目文件的路径,也是把「治理模型属于项目本身」这条原则落地的地方。
2. **运行入口** —— `run` 读取配置、驱动编排、写出运行记录。

CLI 本身**不承担治理判定**。Policy 校验、范围检查、闸门执行、阶段通过与否全部委托给 Core。

## 2. 命令与时机

| 命令 | 什么时候用 | 是否写文件 |
| -------- | ---------------------- | ---------------------------------- |
| `init` | 新项目接入 Harness | 写;已存在且内容不同则跳过 |
| `diff` | 想先看会改什么 | **不写** |
| `update` | Preset 改版后同步模板 | 写 `missing`;`modified` 需要 `--force` |
| `verify` | 提交前、CI | 不写 |
| `doctor` | 排查环境 | 不写 |
| `run` | 执行一次任务 | 写运行记录,可能改产品文件 |

`init` 的幂等规则是整套流程的基础:**不存在则创建,已存在且相同则跳过,已存在且不同则保留并提示,
只有显式 `--force` 才覆盖。** 因此重复执行 `init` 是安全的,也不会静默覆盖用户改过的配置。

## 3. 一次 `run` 里 CLI 做什么

CLI 是编排的宿主,但每个阶段的判定都在 Core:

```text
读 .harness/policy.json 与 agents.json → validatePolicy
        ↓
归一化输入(--task / --prompt / --input 三选一)
        ↓
写 .harness/runs/<runId>/{input,policy}.json        ← 在快照窗口之前
        ↓
runOrchestrator:planner → coder → tester → reviewer
        ↓
每轮写 iteration-<n>-verification.json              ← 在快照窗口之后
        ↓
写 output.json,并按 --json / --output 输出 RunResult
```

CLI 在这里的职责是**准备与记录**:准备配置与任务,记录运行产物。它不做通过与否的判断。

一个容易忽略的细节:CLI 在编排开始前写 `input.json` / `policy.json`,在编排结束后写
`output.json`,所以这些文件**不会**被误判成 Coder 的产品改动——范围判定窗口恰好是一次 Coder 调用。

## 4. 如何参与决策

CLI 不产生治理判定,但有两个决策点由它实现:

| 决策 | 位置 | 内容 |
| -------------- | -------------- | -------------------------------------------------------- |
| 配置是否可用 | `verify` | schema 齐全、JSON 可解析、Policy 合法、闸门脚本存在 |
| 输入是否充分 | `run` 的 intake | `needs_input` 时打印问题并停止,而不是替用户猜 |

intake 的行为值得注意:缺少目标或验收标准时**不报错**,而是转成待回答的问题。这让「信息不足」
与「执行失败」成为两种不同的结果——前者可以补信息后重跑,后者需要修配置或代码。

`verify` 还有一个可扩展点:若项目存在 `.harness/verify.mjs`,CLI 会以 `--root <项目根>` 调用它,
并**透传它的退出码**。这条钩子只在 `verify` 中执行,`run` 流程不会调用它。

## 5. `doctor` 是报告,不是检查

`doctor` 打印四行环境信息(项目根、配置是否存在、包管理器、Node 版本),**不做任何断言**。它不会
因为 Provider 未配置或闸门脚本缺失而失败——那些是 `verify` 的职责。把它当作排查的起点。

## 6. 与 Preset 的关系

`init` 是 Preset 唯一的消费者:它把 `preset.policy`、`preset.agents`、`preset.instruction` 原样
展开成目标项目的文件。schema 与示例任务来自 CLI 内置模板,**与 Preset 无关**。

> **目标(M16)** Preset 将改为以 npm 包分发,`init --preset <name>` 只把包名写进
> `.harness/harness.json`,内容由解析器在运行时加载,而不再复制进项目;Preset 也不再是模板文件的
> 集合。当前**未实现**——`--preset` 目前只能取内置的两个名字(`generic`、`vue`),没有 npm 发现、
> 没有继承、没有配置合并。

见 [Preset 架构](./preset.md)与[Preset 契约](../interfaces/preset.md)。

## 7. 已知限制

| 限制 | 说明 |
| ------------------ | -------------------------------------------------------------- |
| 退出码无分类 | 只有 `0`/`1`,调用方无法区分「策略拒绝」「验证失败」「输入非法」 |
| 无审批交互 | 不存在人工审批门;`run` 不会中途停下来等人 |
| 无 `--host` 概念 | CLI 面向单机一次性任务,不是常驻服务 |

> **目标(M9/M10)** 退出码分类与「等待审批」运行状态属于规划中,当前**未实现**。
