# ADR-004 — Policy 严重级别规则层

* **Status:** Accepted
* **Date:** 2026-09-17
* **Related:** [ADR-003](./ADR-003-preset-as-code.md)、[ADR-002](./ADR-002-preset-validation-resolution.md)

## 1. Context

M7 要让 Policy 真正可执行，但当前 Policy 只能表达四类判定：允许改哪些文件、允许跑哪些命令、必须
通过哪些闸门、最多重试几次——全部是集合与布尔语义，见 [Policy 契约](../interfaces/policy.md)。

治理还需要第五类判定：**检测到的问题有多严重、应该怎么处置**。例如：

| 发现                             | 期望处置             |
| -------------------------------- | -------------------- |
| 新增了一个没有理由的依赖         | 直接拒绝             |
| 新增了一个只被引用一次的组件     | 需要 Reviewer 确认   |
| 缺少非必需文档                   | 记录即可             |

一个扁平设置对象表达不了"同一类问题在不同项目里处置不同"。同时[成本权衡](../tradeoffs/成本权衡.md)
已经确立"确定性问题交给脚本，语义问题交给 LLM"：判定结果必须先有级别，才能决定后续由谁处置。

## 2. Decision

Policy 引入**严重级别规则层**：规则实现产生 Finding，Policy 声明 `rule id → 严重级别 → 处置`。

### 2.1 三个概念

| 概念       | 含义                                                             | 由谁产生       |
| ---------- | ---------------------------------------------------------------- | -------------- |
| `Finding`  | 一条判定结果：rule id、目标、级别、说明、是否可修复               | 规则实现       |
| `Severity` | `error` / `warning` / `info`                                     | 规则默认值，可被 Policy 覆盖 |
| `Action`   | `reject` / `review` / `report`                                   | Policy         |

### 2.2 默认映射

| Severity  | 默认 Action | 含义                         |
| --------- | ----------- | ---------------------------- |
| `error`   | `reject`    | 判定不通过                   |
| `warning` | `review`    | 需 Reviewer 确认后才算通过   |
| `info`    | `report`    | 只记录，不影响判定           |

映射表本身可被 Policy 覆盖；覆盖同样是声明，不是逻辑。

### 2.3 声明与实现的分工

* **实现侧**负责"匹配"：内置 checker 或 Preset 注册的规则决定什么时候产生 Finding。
* **声明侧**负责"处置"：`policy.json` 决定每个 rule id 的级别与动作。
* Policy **不**承载条件表达式、不引入 DSL、不做优先级冲突解决——这三项仍留给 M19 的安全模型。

这条分工是本次决定的核心：它让 severity 进入声明层（用户决策 2），同时避免把 `policy.json` 变成
规则引擎。

> **澄清（[ADR-007](./ADR-007-rule-kinds-and-constraints.md)）** 「不引入 DSL」约束的是**处置侧**：
> `policy.json` 里不写条件表达式。**检测侧**允许声明式约束——一个检查声明自己依据什么事实、与什么值
> 比较（`{ property, operator, value }`）。规则还按种类（`constraint` / `preference` / `instruction` /
> `verification`）决定默认合并语义与默认级别，`kind` 由规则声明设定，项目只能收紧 severity。

### 2.4 统一 Policy Evaluator

文件、命令、规则三类判定必须由同一个 Policy 模块给出结论（M7 已列的工作项）。当前"文件一套逻辑、
命令一套逻辑"已经存在语义漂移的风险，再加入规则层会让它变成三套。

### 2.5 安全约束只能收紧

严重级别属于安全语义：更高层可以把规则**收紧**（`warning` 提升为 `error`、把 `report` 改为 `reject`），
但不能**放宽**——降低级别、`enabled: false`、把 `reject` 改成 `report` 都属于放宽，必须被拒绝。
这与[项目目标](../项目目标.md) 原则 13 和 M19 一致。

## 3. Consequences

### Positive

* 处置第一次可以被项目声明、被审计，而不是写死在实现里。
* 同一条规则在不同项目/不同层级可以得到不同处置。
* 脚本产出的确定性证据与 LLM 产出的语义判定有了统一落点。

### Negative

* Policy 从"扁平设置"变成"设置 + 规则处置表"，加载与校验面变大。
* `rule id` 成为跨包契约，需要命名与版本约定（Preset 提供规则，项目声明处置）。
* 处置与匹配分离后，排障需要同时看 Finding 与 Policy。

明确不在本次范围内：按任务风险裁剪哪些规则生效（成本分级仍未落地，见[成本权衡](../tradeoffs/成本权衡.md)
第 5 节）。

## 4. Alternatives

| 方案                                   | 为什么没选                                                     |
| -------------------------------------- | -------------------------------------------------------------- |
| severity 写死在规则实现里              | 处置无法由项目声明，违反"治理定义进入版本库"                   |
| 每个 Preset 自带 Gate，自行决定处置    | 处置分散在各包，无法审计，也无法实施 deny-wins                 |
| Policy 直接支持条件表达式（规则引擎）  | 声明层承载匹配逻辑后，安全约束的合并（deny-wins）无法静态判定  |

## 5. Core Principle

> **规则实现回答"发现了什么"，Policy 回答"这有多严重、该怎么处置"。**
