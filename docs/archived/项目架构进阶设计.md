我看完了目前 `pedyc-harness` 的 README、`Policy`、`Preset` 和 Core 接口设计。我的判断比较明确：

**应该做成“配置驱动”，但不要把所有配置塞进一个 `harness.json`；同时保留 `.harness/` 作为 Harness 的项目工作区。**

更准确地说，未来应该形成：

> **npm 负责安装能力，`.harness/` 负责声明项目治理策略，Preset 负责复用默认能力，团队仓库负责共享组织级配置。**

你现在其实已经走到了这个方向，只是还可以把边界再明确一层。当前项目已经采用 Core / CLI / Preset 分层，并且 README 已经明确把 `.harness/` 定义为项目级配置位置；Preset 也被设计成“默认能力集合”，项目可以覆盖 Preset 默认值。([GitHub][1])

# 一、我不建议把配置放进 `package.json`

例如：

```json
{
  "dependencies": {
    "pedyc-harness": "^1.0.0"
  },
  "harness": {
    "preset": "vue",
    "policy": {},
    "verification": {}
  }
}
```

**不建议把它作为主方案。**

原因不是 `package.json` 不能做到，而是语义不太对。

`package.json` 的核心职责是：

```text
Project
├── dependencies
├── scripts
├── engines
└── package metadata
```

而 Harness 配置实际上描述的是：

```text
Project
├── Agent Policy
├── Security Boundary
├── Verification
├── Approval
├── Agent Adapter
├── Governance
└── Audit
```

这两套东西未来会越来越不一样。

尤其你的 Harness 后面肯定不只是：

```json
{
  "allowedPaths": [],
  "allowedCommands": []
}
```

而会逐渐出现：

```text
policy
verification
approval
providers
agents
presets
rules
hooks
budgets
audit
security
```

全塞进去以后：

```text
package.json
    ↓
越来越像
harness.json
```

反过来还会让 Harness 的 schema 生命周期被 npm 项目的 schema 生命周期绑架。

# 二、`.harness/` 应该成为真正的核心

这一点我反而建议你坚定下来。

你现在 README 已经规定：

```text
.harness/
```

作为项目级 Harness 配置目录。([GitHub][1])

我认为应该把它进一步正式化成：

```text
.harness/
├── harness.json
├── policy.json
├── verification.json
├── agents.json
├── rules/
├── presets/
├── tasks/
├── hooks/
└── runs/
```

但是这里有一个很重要的设计：

**不要要求用户必须手动维护这么多文件。**

也就是说：

```text
复杂项目
    ↓
拆多个文件

简单项目
    ↓
只需要 harness.json
```

例如最简单项目：

```text
my-project/
├── src/
├── package.json
└── .harness/
    └── harness.json
```

```json
{
  "$schema": "https://pedyc.dev/schema/harness.json",
  "version": 1,
  "preset": "vue"
}
```

而大型团队项目可以：

```text
.harness/
├── harness.json
├── policy.json
├── verification.json
├── agents.json
└── rules/
    ├── architecture.json
    ├── security.json
    └── testing.json
```

这样可扩展性非常好。

# 三、我建议把 `harness.json` 定位成“入口配置”，而不是所有配置

这是我认为最重要的一点。

不要让：

```text
harness.json
```

成为一个 1000 行 JSON。

而应该让它类似：

```json
{
  "$schema": "https://pedyc.dev/schema/harness.json",

  "version": 1,

  "preset": "vue",

  "policy": "./policy.json",

  "verification": "./verification.json",

  "agent": {
    "provider": "claude-code"
  }
}
```

它更像一个：

> **Harness Manifest**

也就是：

```text
harness.json
      ↓
告诉 Runtime：
“这个项目使用什么 Harness”
“加载哪些 Policy”
“加载哪些 Verification”
“使用什么 Agent”
“继承哪些 Preset”
```

而不是把全部细节写进去。

# 四、Preset 应该成为整个生态最重要的一层

你现在的设计已经有这个意识：

```text
@pedyc/harness-preset-generic
@pedyc/harness-preset-vue
```

Preset 本质上是：

> 一套别人已经设计好的 Harness 治理策略。

你现在的文档里也已经明确说，Preset 可以提供：

```text
Policy Defaults
+
Verification Defaults
+
Project Templates
```

然后项目配置覆盖 Preset 默认值。([GitHub][2])

我建议把这个思想进一步扩大。

最终用户体验应该变成：

```bash
npm install -D pedyc-harness
npx harness init --preset vue
```

生成：

```text
.harness/
    harness.json
```

里面：

```json
{
  "version": 1,

  "preset": [
    "@pedyc/harness-preset-vue"
  ]
}
```

甚至可以：

```json
{
  "preset": [
    "@pedyc/harness-preset-vue",
    "@company/harness-preset-team"
  ]
}
```

然后 Runtime：

```text
                    ┌──────────────────┐
                    │ Generic Preset   │
                    └────────┬─────────┘
                             ↓
                    ┌──────────────────┐
                    │ Vue Preset      │
                    └────────┬─────────┘
                             ↓
                    ┌──────────────────┐
                    │ Company Preset   │
                    └────────┬─────────┘
                             ↓
                    ┌──────────────────┐
                    │ Project Config   │
                    └────────┬─────────┘
                             ↓
                    ┌──────────────────┐
                    │ Task Config      │
                    └──────────────────┘
```

这会非常强。

# 七、因此你需要一个“配置解析器”

未来 Core 中应该出现类似：

```ts
type HarnessConfig = {
  version: number
  extends?: string[]
  preset?: string[]
  policy?: PolicyConfig
  verification?: VerificationConfig
  agent?: AgentConfig
}
```

然后：

```text
loadConfig()
      ↓
resolvePreset()
      ↓
resolveExtends()
      ↓
mergeConfig()
      ↓
validateSchema()
      ↓
EffectiveHarnessConfig
```

最终 Runtime 根本不关心：

```text
这个 policy 来自哪里？
```

它只拿：

```ts
EffectiveHarnessConfig
```

运行。

也就是说：

```text
Preset
Team Preset
Project Config
Task Config
        ↓
    Config Resolver
        ↓
Effective Config
        ↓
Harness Runtime
```

这会让你的 Core 保持干净。

# 八、这里必须特别注意一个问题：不是所有配置都允许 merge

这是你这个项目后期非常容易踩坑的地方。

例如：

```json
{
  "protectedPaths": [
    ".env",
    ".github"
  ]
}
```

这个很好：

```text
Preset A
protected = [".env"]

+
Preset B
protected = [".github"]

↓

[".env", ".github"]
```

但是：

```json
{
  "forbiddenCommands": []
}
```

可以继承。

而：

```json
{
  "allowedCommands": []
}
```

到底是：

```text
replace
```

还是：

```text
merge
```

就必须定义。

更危险的是：

```json
{
  "protectedPaths": [
    ".harness"
  ]
}
```

项目能不能覆盖？

答案应该是：

**不能。**

因为你现在 Policy 文档已经定义了：

```text
protectedPaths > allowedPaths
```

并且 `.harness/` 本身就是保护目录。([GitHub][3])

所以配置系统不能只是：

```ts
deepMerge(a, b)
```

这种普通对象 merge。

应该拥有：

```text
Config Merge Semantics
```

例如：

```ts
type MergeStrategy =
  | "replace"
  | "merge"
  | "append"
  | "deny-wins"
  | "immutable"
```

这是未来非常值得提前设计的。

# 九、还有一个我认为比 `harness.json` 更重要的问题：哪些东西应该进入 Git？

我建议明确区分：

```text
Definition
vs
Runtime State
```

比如：

### 应该提交

```text
.harness/
├── harness.json
├── policy.json
├── verification.json
├── rules/
└── tasks/
```

这些属于：

> **Governance Definition**

### 不应该提交

```text
.harness/
└── runs/
    ├── 2026-09-16-001/
    ├── 2026-09-16-002/
    └── ...
```

因为这是：

> **Runtime State / Audit Data**

所以未来甚至可以：

```text
.harness/
├── config/
├── rules/
├── tasks/
└── .runtime/
```

或者：

```text
.harness/
├── harness.json
├── policy.json
├── verification.json
└── runtime/
```

然后 `.gitignore`：

```gitignore
.harness/runtime/
```

这样就非常清晰。

# 十三、个人 Preset 也可以成立

甚至可以：

```text
@pedyc/my-harness-preset
```

或者本地：

```text
~/.pedyc/harness/presets/
```

于是出现：

```text
Global personal preferences
        ↓
Team governance
        ↓
Project governance
        ↓
Task governance
```

但这里有一个边界：

**个人 Preset 不能突破组织/项目的安全约束。**

例如：

```text
个人 preset：
允许 git push
```

但：

```text
公司 preset：
禁止 git push
```

最终必须：

```text
DENY
```

而不是：

```text
个人配置覆盖公司配置
```

所以配置层级实际上不是简单的：

```text
lower → higher override
```

而应该是：

```text
Convenience defaults
        ↓
Project policy
        ↓
Organization policy
        ↓
Security invariants
```

其中安全类 Policy 应该存在：

> **不可覆盖规则**

## 最终我的建议

你提出的三个方案里，我的排序是：

| 方案                    | 建议               |
| ----------------------- | ------------------ |
| `package.json` 里配置   | ❌ 不作为主方案     |
| `.harness/harness.json` | ✅ **核心方案**     |
| `.harness/` 多文件配置  | ✅ **后期扩展方案** |
| npm Preset              | ✅ **强烈推荐**     |
| 团队 Preset             | ✅ **应该做**       |
| 个人 Preset             | ✅ 可以做           |
| 自建 Registry           | ⏳ 后期再做         |

最终的用户心智应该非常简单：

```bash
npm install -D pedyc-harness
```

项目：

```text
.harness/
└── harness.json
```

配置：

```json
{
  "extends": [
    "@pedyc/harness-preset-vue",
    "@company/harness-preset"
  ]
}
```

然后：

```bash
npx harness run
```

**安装的是 Harness 能力，`harness.json` 声明项目治理模型，Preset 提供可复用治理能力，Runtime 负责把这些声明编译成真正可执行的 Policy。**

我认为这条路线比单纯模仿 `package.json` 更适合 `pedyc-harness`，也更符合你目前已经建立的 Core / Preset / Policy / Verification 架构。([GitHub][2])
