# pedyc-harness 算法设计

> 本文用于梳理 `pedyc-harness` 中涉及的核心算法、数据结构、复杂度与未来优化方向。
>
> 目标不是追求“使用更多算法”，而是建立一张算法地图，使后续功能设计、性能优化和架构重构都有明确的算法依据。

---

# 1. 算法总览

`pedyc-harness` 本质上是一个：

> **Policy-driven AI Agent Runtime**

它需要解决的核心问题可以抽象为：

```text
配置
  ↓
依赖解析
  ↓
Policy 组合
  ↓
Task / Action 分析
  ↓
Scope 判断
  ↓
Policy Evaluation
  ↓
Verification
  ↓
Evidence
  ↓
Gate
  ↓
Audit
```

因此涉及的算法主要集中在以下几个领域：

| 领域         | 核心算法 / 数据结构                  | 重要程度 |
| ------------ | ------------------------------------ | -------: |
| Preset 依赖  | DFS / DAG / 拓扑排序                 |    ⭐⭐⭐⭐⭐ |
| 配置合并     | Tree Merge / Constraint Merge        |    ⭐⭐⭐⭐⭐ |
| Policy 判断  | Rule Matching / Predicate Evaluation |    ⭐⭐⭐⭐⭐ |
| Scope 判断   | Path Matching / Trie / Glob Matching |    ⭐⭐⭐⭐⭐ |
| 权限判断     | Set / HashSet / Capability Matching  |    ⭐⭐⭐⭐⭐ |
| Verification | Pipeline / Dependency Graph          |     ⭐⭐⭐⭐ |
| Task 执行    | State Machine                        |    ⭐⭐⭐⭐⭐ |
| Evidence     | Hash / Content Addressing            |     ⭐⭐⭐⭐ |
| Audit        | Append-only Log                      |      ⭐⭐⭐ |
| Diff         | Tree Diff / Sequence Diff            |     ⭐⭐⭐⭐ |
| 缓存         | Memoization / Content Hash           |     ⭐⭐⭐⭐ |
| 配置加载     | Dependency Resolution                |    ⭐⭐⭐⭐⭐ |
| 并发执行     | DAG Scheduling                       |     ⭐⭐⭐⭐ |
| 风险控制     | Rule Aggregation / Deny-wins         |    ⭐⭐⭐⭐⭐ |

# 2. Preset Dependency Graph

## 2.1 问题

Preset 可以继承其他 Preset：

```text
project
   ↓
@company/frontend
   ↓
@company/base
   ↓
@pedyc/web
   ↓
@pedyc/base
```

甚至可能出现多个父依赖：

```text
             base
            /    \
           ↓      ↓
         web    security
           \      /
            ↓    ↓
           company
              ↓
            project
```

因此 Preset 不是简单的树，而应该视为：

> Directed Acyclic Graph（DAG）

---

# 3. DFS：Preset 依赖解析

## 3.1 为什么使用 DFS

Preset 的依赖关系天然适合 DFS：

```text
resolve(A)
 ├── resolve(B)
 │    └── resolve(D)
 └── resolve(C)
      └── resolve(D)
```

需要解决：

1. 递归加载依赖
2. 避免重复加载
3. 检测循环依赖
4. 获得依赖优先级

---

## 3.2 三状态模型

Preset Resolver 应使用三种状态：

```text
UNVISITED
VISITING
VISITED
```

例如：

```ts
type VisitState =
  | "unvisited"
  | "visiting"
  | "visited";
```

算法：

```text
UNVISITED
    ↓
VISITING
    ↓
VISITED
```

如果：

```text
VISITING → VISITING
```

说明存在循环依赖。

例如：

```text
A → B → C → A
```

最终：

```text
A
↓
B
↓
C
↓
A  ← circular dependency
```

---

## 3.3 复杂度

设：

```text
V = Preset 数量
E = Preset dependency 数量
```

DFS：

```text
Time:  O(V + E)
Space: O(V)
```

对于正常项目，这已经足够高效。

---

# 4. Topological Sort

DFS 不只是用来搜索，还可以产生：

> Topological Order

例如：

```text
A
↓
B
↓
C
```

得到：

```text
[A, B, C]
```

或者：

```text
base
├── web
└── security
      ↓
    company
```

得到：

```text
base
web
security
company
```

这样可以保证：

> 父 Preset 在子 Preset 之前被解析。

---

## 4.1 为什么不能只靠加载顺序

不能简单：

```ts
presets.forEach(load)
```

因为：

```text
Project
 ↓
Company
 ↓
Web
 ↓
Base
```

用户声明顺序不代表依赖顺序。

必须先解析：

```text
dependency graph
```

然后：

```text
topological order
```

---

# 5. Preset 去重

多个 Preset 可能依赖同一个 Preset：

```text
Company
├── Web
│    └── Base
└── Security
     └── Base
```

Base 不能加载两次。

使用：

```ts
Set<string>
```

记录：

```text
resolvedPresets
```

复杂度：

```text
Lookup: O(1)
```

因此：

```text
DFS + Set
```

是 Preset Resolver 的基础实现。

---

# 6. Preset Version Resolution

Preset 使用 npm package，因此版本解析尽量交给 npm。

例如：

```text
@company/harness-preset
        ↓
@pedyc/harness-web ^2.0.0
```

Harness 不应该重新实现 npm 的 SemVer Resolver。

职责应该是：

```text
npm
 ↓
安装正确版本
 ↓
node_modules
 ↓
Harness
 ↓
读取 preset.json
```

Harness 自己主要解决：

```text
Preset dependency graph
```

而不是：

```text
Package dependency resolution
```

# 7. 配置合并算法

Preset 加载之后，需要生成：

```text
EffectiveConfig
```

例如：

```text
Base Preset
      +
Web Preset
      +
Company Preset
      +
Project Config
```

最终：

```text
Effective Harness Config
```

# 8. Tree Merge

配置本质上是 JSON Tree：

```text
Config
├── policy
│   ├── paths
│   └── commands
├── verification
│   ├── test
│   └── build
└── agent
```

因此配置合并可以抽象为：

```text
Tree Merge
```

但是不能简单使用：

```ts
deepMerge(a, b)
```

因为不同字段有不同语义。

---

# 9. Merge Strategy

建议定义：

```ts
type MergeStrategy =
  | "replace"
  | "merge"
  | "append"
  | "deny-wins"
  | "immutable";
```

例如：

## replace

```json
{
  "timeout": 30
}
```

后者覆盖前者：

```text
30 → 60
```

---

## append

例如：

```text
protectedPaths
```

```text
A = [".env"]
B = ["infra"]

A + B

= [".env", "infra"]
```

---

## deny-wins

例如：

```text
allowedCommands
forbiddenCommands
```

最终：

```text
DENY > ALLOW
```

---

## immutable

某些安全约束不能被下层配置覆盖：

```text
.harness
.env
production
```

# 10. Policy Rule Matching

Policy Engine 的核心问题：

> 给定一个 Action，判断它是否满足 Policy。

例如：

```json
{
  "action": "write",
  "path": "src/foo.ts"
}
```

Policy：

```json
{
  "allow": [
    "src/**"
  ],
  "deny": [
    ".env",
    ".github/**"
  ]
}
```

需要执行：

```text
Action
 ↓
Rule Matching
 ↓
ALLOW / DENY / REQUIRE_APPROVAL
```

---

# 11. Path Matching

Path Policy 很可能是 Harness 中最频繁执行的算法之一。

例如：

```text
src/**
tests/**
.env
.github/**
```

需要判断：

```text
src/a.ts
src/components/Button.tsx
.env
.github/workflows/test.yml
```

是否匹配。

---

## 11.1 第一阶段

直接使用 Glob Matching：

```text
O(pattern length + path length)
```

对于几十、几百条规则已经足够。

---

# 12. Path Trie

如果未来出现：

```text
10,000+
```

条 Path Policy，应该考虑 Trie。

例如：

```text
src/
├── components/
│   ├── Button.tsx
│   └── Input.tsx
├── pages/
└── utils/
```

Trie 可以共享：

```text
src
components
```

这些公共前缀。

适合：

```text
Path Prefix
```

大量匹配场景。

---

# 13. Glob Pattern Compilation

如果规则经常执行：

```text
src/**
tests/**
*.config.ts
```

可以在加载 Policy 时预编译：

```text
Glob Pattern
     ↓
Compiled Matcher
```

而不是每一次 Action 都重新解析 Pattern。

即：

```text
load policy
    ↓
compile patterns
    ↓
cache matcher
    ↓
evaluate action
```

这是一个典型的：

> Precomputation Optimization

---

# 14. Command Matching

Command Policy 可能类似：

```text
npm test
npm run build
git diff
git status
```

需要判断：

```text
command
 ↓
normalize
 ↓
match rule
 ↓
decision
```

这里需要特别注意：

```text
字符串匹配
```

并不等于：

```text
安全的命令解析
```

例如：

```bash
npm test && rm -rf /
```

不能简单认为：

```text
startsWith("npm test")
```

因此后续应该建立：

> Command Parser / Normalizer

把 Command 转换成结构化 AST：

```text
Command
   ↓
Parser
   ↓
Command AST
```

然后 Policy 针对 AST 判断。

---

# 15. Set / HashSet

大量 Policy 判断都会使用集合：

```text
protectedPaths
allowedCommands
forbiddenCommands
capabilities
verifiedSteps
```

应该优先使用：

```ts
Set
Map
```

而不是：

```ts
Array.includes()
```

例如：

```text
Array lookup:
O(N)

Set lookup:
O(1) average
```

当 Policy 规模扩大后差距会明显。

---

# 16. Policy Evaluation

最终 Policy Evaluation 可以抽象为：

```text
Action
 ↓
Normalize
 ↓
Match Rules
 ↓
Collect Decisions
 ↓
Resolve Conflicts
 ↓
Final Decision
```

例如：

```ts
type Decision =
  | "allow"
  | "deny"
  | "require_approval";
```

---

# 17. Deny-Wins

对于安全策略，建议采用：

```text
DENY
  >
REQUIRE_APPROVAL
  >
ALLOW
```

例如：

```text
Rule A → ALLOW
Rule B → DENY
Rule C → ALLOW
```

最终：

```text
DENY
```

这可以避免：

```text
后加载规则覆盖安全规则
```

---

# 18. Policy Evaluation 优化

如果每一个 Action 都遍历全部 Rule：

```text
Action × Rules
```

复杂度：

```text
O(A × R)
```

其中：

```text
A = Action 数量
R = Rule 数量
```

未来可以按照：

```text
action type
path prefix
command
resource
```

进行索引。

例如：

```text
rulesByActionType

rulesByPathPrefix

rulesByCommand
```

让 Rule Matching 从：

```text
O(R)
```

降低到：

```text
O(K)
```

其中 K 是相关规则数量。

---

# 19. Task State Machine

Harness 执行过程不是简单函数调用。

一个 Task 可能经历：

```text
created
   ↓
planned
   ↓
approved
   ↓
executing
   ↓
verifying
   ↓
completed
```

或者：

```text
executing
   ↓
failed
   ↓
retrying
   ↓
executing
```

因此应该建模为：

> Finite State Machine（FSM）

---

# 20. Task State

例如：

```ts
type TaskState =
  | "created"
  | "planned"
  | "waiting_approval"
  | "executing"
  | "verifying"
  | "completed"
  | "failed"
  | "cancelled";
```

定义合法 Transition：

```text
created
  → planned

planned
  → waiting_approval
  → executing

waiting_approval
  → executing
  → cancelled

executing
  → verifying
  → failed

verifying
  → completed
  → failed
```

非法 Transition：

```text
completed
  → executing
```

必须拒绝。

# 21. Verification Pipeline

Verification 可以抽象为 Pipeline：

```text
Change
 ↓
TypeCheck
 ↓
Lint
 ↓
Test
 ↓
Build
 ↓
Policy Gate
```

每一步：

```text
Input
 ↓
Verification
 ↓
Evidence
```

# 22. Verification Dependency Graph

未来 Verification 不一定是线性的。

例如：

```text
             TypeCheck
             /       \
            ↓         ↓
          Lint       UnitTest
             \       /
              ↓     ↓
                Build
                  ↓
                 Gate
```

这实际上又是一个 DAG。

因此 Verification Engine 可以复用：

```text
Graph
DFS
Topological Sort
```

---

# 23. 并行 Verification

如果：

```text
TypeCheck
Lint
UnitTest
```

互不依赖，可以并行：

```text
             ┌→ TypeCheck ─┐
Change ──────┼→ Lint ──────┼→ Build
             └→ UnitTest ──┘
```

因此可以根据 DAG 计算：

> Dependency Level

然后：

```text
Level 0 → 并行执行
Level 1 → 并行执行
Level 2 → 并行执行
```

这是后期性能优化的重要方向。

---

# 24. Evidence Hash

Verification 产生：

```text
Evidence
```

例如：

```json
{
  "type": "test",
  "command": "npm test",
  "status": "passed",
  "timestamp": "...",
  "output": "..."
}
```

可以计算：

```text
SHA-256(Evidence)
```

获得：

```text
Evidence ID
```

例如：

```text
evidence:
sha256:abc123...
```

这样可以用于：

```text
去重
缓存
完整性验证
Audit
```

---

# 25. Content Hash / Cache Key

Verification 很适合缓存。

例如：

```text
Source Hash
+
Policy Hash
+
Verification Config Hash
```

计算：

```text
Cache Key
```

：

```text
H(
  source
  policy
  verification
)
```

如果：

```text
CacheKey(old) === CacheKey(new)
```

则理论上可以复用：

```text
Verification Evidence
```

这是后续非常重要的性能优化方向。

---

# 26. Incremental Verification

大型项目中：

```text
修改 1 个文件
```

不应该每次：

```text
重新检查整个项目
```

而应该分析：

```text
Changed Files
       ↓
Dependency Graph
       ↓
Affected Modules
       ↓
Affected Tests
       ↓
Affected Verification
```

这属于：

> Incremental Computation

例如：

```text
Button.tsx
   ↓
Button.test.tsx
   ↓
Component test
```

而不是运行整个测试集。

# 27. Diff Algorithm

Harness 需要知道：

```text
Before
vs
After
```

因此需要 Diff。

至少包括：

```text
File Diff
Line Diff
Structured Config Diff
Policy Diff
```

---

# 28. Tree Diff

对于：

```text
Policy
Config
Evidence
Task
```

这些结构化数据，应该使用 Tree Diff：

```text
Old Tree
    ↓
Tree Diff
    ↓
Change Set
```

输出：

```text
ADD
REMOVE
MODIFY
MOVE
```

---

# 29. Change Set

建议内部统一定义：

```ts
type Change = {
  type: "add" | "remove" | "modify";
  path: string;
  before?: unknown;
  after?: unknown;
};
```

这样：

```text
Policy
Diff
Review
Audit
Verification
```

都可以复用 Change Model。

---

# 30. Audit Log

Audit 不应该依赖复杂算法。

核心应该是：

> Append-only Log

例如：

```text
Event 1
Event 2
Event 3
Event 4
```

而不是不断修改：

```text
audit.json
```

这样可以保持：

```text
时间顺序
可追踪性
不可变性
```

---

# 31. Event Hash Chain

未来如果需要增强 Audit 完整性，可以：

```text
hash(Event1)
      ↓
hash(Event2 + hash1)
      ↓
hash(Event3 + hash2)
```

形成：

```text
Event1
   ↓
Event2
   ↓
Event3
   ↓
Event4
```

如果中间事件被修改：

```text
hash chain
```

会断裂。

这不是区块链，而是简单的：

> Hash Chain

适合 Audit Integrity。

可能出现多个缓存：

```text
Preset Cache
```

统一可以使用：

```text
Map<Key, Value>
```

# 33. Memoization

适合缓存：

```text
resolvePreset(name)
compileGlob(pattern)
evaluatePolicy(action)
```

例如：

```text
evaluatePolicy(action)
```

如果：

```text
Policy Hash
+
Action Hash
```

相同，可以直接返回之前结果。

# 34. Deterministic Execution

Harness 最重要的算法设计原则之一：

> 相同输入应该产生相同 Policy Decision。

即：

```text
Policy
+
Action
+
Context
```

应该决定：

```text
Decision
```

而不是：

```text
Agent 今天怎么想
```

所以 Policy Engine 应尽量：

```text
Pure Function
```

即：

```ts
evaluate(
  policy,
  action,
  context
): Decision
```

不要在里面：

```text
修改全局状态
读取随机值
依赖时间
依赖 Agent 输出
```

---

# 35. Rule Normalization

不同来源的 Policy：

```text
Preset
Company
Project
Task
```

最终应该先 Normalization：

```text
Raw Rule
 ↓
Normalize
 ↓
Canonical Rule
 ↓
Evaluation
```

例如：

```text
src/**
./src/**
src/**/
```

可以统一成 Canonical Representation。

这样可以：

```text
减少重复
方便缓存
提高匹配性能
```

---

# 36. Config Canonicalization

类似地，Config 应该能够生成稳定表示：

```text
Config
 ↓
Canonical JSON
 ↓
Hash
```

这样：

```text
Config Hash
```

可以作为：

```text
Cache Key
Evidence Reference
Audit Reference
```

# 37. Dependency Graph Cache

Preset Graph 如果没有变化，就没有必要每次重新解析。

可以缓存：

```text
Preset Package Version
+
preset.json hash
```

例如：

```text
@acme/harness-preset@1.2.0
```

对应：

```text
Resolved Graph
```

如果 package lock 没变化，可以复用。

可以形成：

```text

                   │
             ┌─────┴─────┐
             ↓           ↓
            DFS       Topological Sort
             │           │

                   │
                   ↓

                   │
                   ↓
             Rule Normalization
                   │
             ┌─────┴──────┐
             ↓            ↓

             │            │
             └─────┬──────┘
                   ↓
            Policy Evaluation
                   │
                   ↓
               Decision
                   │
                   ↓
              Task FSM
                   │
                   ↓
          Verification DAG
                   │
                   ↓
               Evidence
                   │
                   ↓

                   │
                   ↓

```

# 39. 算法复杂度基线

后续性能优化应以这些基线为参考。

| 算法             | 当前建议         | 时间复杂度 |
| ---------------- | ---------------- | ---------: |
| Preset DFS       | DFS + Set        |   O(V + E) |
| Topological Sort | Kahn / DFS       |   O(V + E) |
| Preset Dedup     | HashSet          |   O(1) avg |
| JSON Tree Merge  | Recursive Merge  |       O(N) |
| Rule Matching    | Linear Scan      |       O(R) |
| Path Matching    | Glob             |       O(P) |
| Set Lookup       | HashSet          |   O(1) avg |
| Task Transition  | State Table      |       O(1) |
| Verification DAG | Topological Sort |   O(V + E) |
| Evidence Hash    | SHA-256          |       O(N) |
| Tree Diff        | Recursive Diff   |   O(N + M) |
| Cache Lookup     | HashMap          |   O(1) avg |

其中：

```text
V = 节点数量
E = 边数量
N = 数据大小
R = Rule 数量
P = Path Pattern 长度
```

# 40. 当前阶段不应该过度优化的算法

`pedyc-harness` 当前不应该一开始就实现：

```text
复杂 Trie
复杂数据库索引
复杂 DAG Scheduler
分布式 Cache
自建 SemVer Resolver
自建 Package Registry
```

原因：

> 算法优化必须建立在真实瓶颈之上。

第一阶段优先：

```text
正确性
可测试性
确定性
可观测性
```

而不是：

```text
极限性能
```

# 41. 优化路线

未来性能优化可以按照：

```text
Phase 1
Linear Algorithm
       ↓
Phase 2
Memoization
       ↓
Phase 3
Index
       ↓

Incremental Computation
       ↓
```

例如 Policy：

```text
Phase 1:

缓存 Rule Matcher

Phase 3:
按 Action Type / Path Prefix 建索引

Phase 4:
只重新计算变化的 Policy

Phase 5:
并行执行互不相关的 Verification
```

# 42. 算法设计原则

## 原则 1：优先使用成熟算法

例如：

```text
DFS
DAG
Topological Sort
HashSet
Memoization
FSM
```

没有必要为了“算法创新”而复杂化。

---

## 原则 2：Policy 优先正确性

安全 Policy：

```text
Correctness > Performance
```

宁可：

```text
多匹配一次
```

也不能：

```text
错误放行
```

---

## 原则 3：安全规则默认 Deny-Wins

：

```text
DENY
  >
APPROVAL
  >
ALLOW
```

---

## 原则 4：Runtime 尽可能确定性

：

```text
same input
+
same policy
+
same context
=
same decision
```

---

## 原则 5：昂贵计算优先缓存

重点候选：

```text
Preset Resolution
Glob Compilation
Policy Evaluation
Config Hash
Verification
```

---

## 原则 6：优化前建立 Benchmark

任何算法优化之前，应该记录：

```text
Input Size
Execution Time
Memory
Cache Hit Rate
Rule Count
Preset Count
Graph Size
```

例如：

```text
Preset Count: 100
Rules: 10,000
Actions: 100,000

Before:
Policy Evaluation = 3.2s

After:
Policy Evaluation = 180ms
```

而不是凭感觉优化。

# 49. 核心思想

`pedyc-harness` 并不是一个“算法很多”的项目。

它真正重要的是：

> **把 AI Agent 的非确定性行为，逐步转换成可以被图、规则、状态机和证据系统约束的确定性执行过程。**

可以概括为：

```text
AI Intent
    ↓
Action
    ↓
Policy
    ↓
Rule Matching
    ↓
Deterministic Decision
    ↓
Execution
    ↓
Verification
    ↓
Evidence
    ↓
Gate
```

其中：

```text
Graph
```

解决：

> **依赖关系**

```text
Rule Engine
```

解决：

> **是否允许**

```text
State Machine
```

解决：

> **现在处于什么状态**

```text
Verification DAG
```

解决：

> **如何验证**

```text
Hash / Evidence
```

解决：

> **如何证明**

这五类算法共同构成 `pedyc-harness` 的算法基础。
