# 文档规范

> `docs/` 的目录语义、每类文档必须回答的问题,以及文档质量的强制检查。
>
> 本文是规范,不是描述。它约束 `docs/` 下的所有文件,包括本文。

---

## 1. 为什么需要本文

`docs/` 的目录语义此前只存在于五个单行 README 中(`docs/architecture/README.md` 等),既没有
可执行的模板,也没有任何检查。结果是:一次目录重构后,全库 156 条相对链接中有 80 条失效
(51%),而没有一道门禁发现它。

本文把这些约定写成可检查的规则。检查由 `pnpm run docs:check` 执行,已接入 CI。

---

## 2. 目录语义

每个目录回答一个不同的问题。文档放错目录,等价于回答错了问题。

| 目录 | 必须回答的问题 |
| ----------------------------- | ---------------------------------------------------------------- |
| `docs/`(根) | 项目的基准与入口:项目是什么、当前阶段、如何阅读其余文档 |
| `docs/architecture/` | **系统结构**:是什么?什么时候执行?如何参与系统决策? |
| `docs/interfaces/` | **接口契约**:类型、签名、模块边界 |
| `docs/decisions/` | **为什么**这么设计(ADR) |
| `docs/milestones/` | **什么时候做什么** |
| `docs/tradeoffs/` | 不同方案之间的**成本** |
| `docs/archived/` | 过期或被替代的方案,仅用于追踪演进,**非规范** |

目录只在确有内容时才存在。`docs/architecture/algorithms/` 曾经存在,现已整体移入
`archived/`,理由见第 3 节末尾。

判据示例:

- 「新增一个功能应该问哪 8 个问题」是决策准则 → `decisions/` 或项目基准,不是 `architecture/`。
- 「配置如何继承与合成」是 Preset 领域 → `architecture/preset.md`,不在 `architecture/system.md`
  重复一遍。
- 「某个类型有哪些字段」是契约 → `interfaces/`,不在 `architecture/` 里贴类型定义。

---

## 3. 每类文档的最低要求

### architecture/

必须能回答是什么、什么时候执行、如何参与系统决策。三者缺一即不合格。不得写成教程,不得大段
复述类型签名(那是 `interfaces/` 的职责),不得把未实现的目标设计用现在时陈述为现状。

### interfaces/

必须与 `packages/` 中真实导出的类型一致。不得发明类型名,不得占用真实导出名去描述另一个形状
(例如用 `Policy` 表示规则引擎,而真实的 `Policy` 是 `.harness/policy.json` 的形状)。只记录契约,
不叙述架构。

### 算法类内容

只描述**已实现**的计算或执行过程。当前实现的内部计算规模很小(执行循环 184 行、策略引擎
35 行、验证是一个串行循环),其契约已由 `interfaces/` 覆盖,执行顺序由
[系统架构](./architecture/system.md) 覆盖——因此不再需要一个独立的算法目录。

> **当子目录里多数文档描述的是尚未构建的子系统时,正确做法是把该目录整体移入 `archived/`,
> 而不是保留目录并逐篇加标注。** `docs/architecture/algorithms/` 就是这样被移除的:6 篇中
> 5 篇描述从未构建的系统,合并 1,696 行,且没有任何一处标注。

### decisions/

采用 ADR 格式,至少包含 Context / Decision / Consequences,并带 `Status` 与 `Date`。后一个 ADR
推翻前一个时,必须显式记录替代关系(`Supersedes` / `Superseded by`),不能只留下两份互相矛盾的
决定。

### milestones/

给出阶段划分与状态表,状态只能取 `已完成` / `计划中`。依赖顺序必须写明。

### tradeoffs/

对比不同方案的成本,而不是记录单方案的设计说明。

### archived/

必须在文首声明其非规范状态,例如:

```md
> **本文是历史设计材料,不是规范。**
```

任何现行文档不得把 `archived/` 中的文件当作权威来源引用。

以上是对归档文档的**内容要求,不由工具强制**(见第 8 节的豁免)。归档文档的数量只会增加,
逐篇补齐声明与重排标题的成本不划算;真正需要保证的是第 8 节那条——现行文档不得留下指向
archive 的死链。

---

## 4. 标题层级

**一份文档只有一个 H1,即文档标题。** 章节用 H2,子章节用 H3。

禁止把每个章节都写成 H1(`# 1.`、`# 2.` …)。这会破坏文档大纲,使目录、锚点与阅读器导航全部
失效,并且让「文档标题」与「章节」在结构上无法区分。

父标题若未闭合(H1 之后直接跳到 H3),同样违反本规范。

---

## 5. 当前实现与目标形态

对系统行为的**现在时陈述,等于声称它已经实现**。因此:

- 描述已实现的行为:直接写。
- 描述尚未实现的设计:必须显式标注,例如
  `> **目标(M16)** …` 或在章节中给出「当前 / 目标」对照表。

不允许在同一文件里混用两种语气而不加标注——读者无法判断哪一段可信。

---

## 6. 链接

- 相对链接相对于**包含它的文件**解析,不是相对于仓库根,也不是相对于 `docs/`。
- 文件移动时,必须在**同一次变更**中修正所有入站链接。重构后再补是本次链接失效 51% 的直接原因。
- 指向空文件的链接视为无效:目标文件必须至少有一行 H1。
- `http(s)://`、`mailto:` 与纯锚点链接不参与检查。
- 锚点(`#section`)必须与目标标题一致。

检查命令:

```bash
pnpm run docs:check
```

---

## 7. 命名与 README 职责

- 新文件使用小写 kebab-case。`docs/` **根目录的专题文档**可以用中文名（如 `项目目标.md`、
  `核心概念.md`），子目录内一律 kebab-case，因为子目录承载的是可导航的结构而不是专题。
  **文件名不得含空格**。
- `docs/README.md` 只负责导航。设计内容进入对应文档,不堆在 README 里。
- 每个子目录的 `README.md` 声明该目录的语义(一到三行),并**充当该目录的索引**:列出目录内的
  成员。导航完整性因此是**传递的**——`docs/README.md` 链接目录 README,目录 README 链接自己的
  成员,否则每个成员都要在顶层列一遍,地图会退化成清单。索引不算设计内容,可以列在这里。
- `docs/index.md` 是站点首页(由 frontmatter 驱动,因此不要求 H1),不参与「README 必须索引所有文档」
  的检查。它是站点的入口,不是设计文档。
- 端到端走查放在**根目录**(如 `getting-started.md`),不另建 `guides/` 目录:只有一个走查时,多一层
  目录只会让读者多一次跳转。走查属于根目录的「入口」语义,回答「从哪开始」。

目录中除 Markdown 之外的站点基础设施:

| 路径 | 作用 |
| ---------------------- | ------------------------------------------------ |
| `docs/.vitepress/` | 站点配置与构建产物(产物已 gitignore) |
| `docs/package.json` | 站点自身的 package,`private`,不参与发布 |
| `docs/scripts/` | 站点自带的检查脚本 |

## 8. 强制检查

检查由**文档站点自身**承担,分两半,合起来构成 `pnpm run docs:check`
(从仓库根执行,委托给 `pnpm --dir docs run check`):

| 检查 | 实现 | 覆盖 |
| -------------- | ------------------------------------ | ------------------------------------------------------------ |
| 规范与链接 | `docs/scripts/check-conventions.mjs` | 标题层级、文件名、空文件链接、导航完整性、**现行文档的出站链接** |
| 站点完整性 | `vitepress build` | 全站路由与锚点;VitePress 在发现死链时直接使构建失败 |

VitePress 只校验**站点根之内**的链接。因此:

- `docs/` 内部的相对链接照常书写。
- 指向站点之外的仓库文件(如根目录的 `CHANGELOG.md`)必须写成 GitHub URL,不能写成 `../CHANGELOG.md`。

**致命(非零退出):**

- 现行文档中的相对链接无法解析(由 `check-conventions.mjs` 判定)。
- VitePress 构建报告死链(由构建判定)。

**警告(仅报告,不阻断):**

- 文档没有 H1,或有多个 H1。
- 标题层级跳级(如 H1 之后直接出现 H3),使该章节没有父级。
- 文件名含空格。
- 链接指向空文件。
- 现行文档未被 `docs/README.md` 直接链接。

`check-conventions.mjs --strict` 可把警告也视为失败,便于日后收紧策略而无需改代码。

### `archived/` 的豁免

`docs/archived/` 保存的是**被替代的历史设计**,不参与强制检查:

- 它不作为检查**来源**:其结构(标题层级、文件名)与**出站链接**都不被校验。
- 它仍然是合法的链接**目标**:现行文档指向 archive 中不存在的条目,依然会被判为致命错误,
  因为此时出错的是现行文档。
- 检查输出会显式列出被忽略的文档数,豁免是可见的,不是静默跳过;站点配置中的
  `ignoreDeadLinks` 与之对应,使历史文档的死链不会中断构建。

保留这一豁免的理由:强制历史文档遵守现行规范会持续产生与维护成本不成比例的噪音,而
`archived/` 的价值在于可追溯,不在于可导航。

之所以把结构问题降为警告:现存文档早于本规范,若立即致命,门禁会长期为红而失去意义。
**致命项必须始终为 0。**
